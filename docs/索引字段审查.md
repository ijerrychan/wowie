# 索引名称、别名与关键词审查

日期：2026-11-07。范围为当前源码，以及本机 `Wowie/app-index-v7.json` 的来源级持久化数据。仅检查索引和生成逻辑，没有读取浏览器的私人书签内容，没有修改搜索行为或用户缓存。

## P0：Shell 控制面板任务的关键词不应等同名称

来源：`src/platform/windows/shell.rs::control_panel_keywords`，通过 Shell 的关键词属性读取并按分号拆分；`src/providers/control_panel.rs` 直接把这些词放入 `aliases`。

实际例子：

- “查看设备和打印机”：258 个别名。
- “设备管理器”：187 个别名。
- “更改日期、时间或数字格式”：184 个别名，包含 `1`、`2`、`3`、`of`、`out`、`set`、`12-hour` 等。
- “管理音频设备”：140 个别名。
- `up` 同时命中 74 项，`set` 命中 51 项，`of` 命中 39 项，`settings` 命中 41 项。

这些是系统为宽松检索准备的词，并不是项目的等价名称。把它们当作名称别名，会让 `set`、`setup` 等短词产生精确匹配，现有标题加分无法跨越匹配层级解决这个问题。

已修部分：源码过滤 1～2 位独立数字关键词，中央搜索也拒绝短纯数字查询只靠别名召回，因此旧缓存里的 `1` 不再需要靠重建才获得保护。

仍需调整：

1. 把 Shell 关键词移入独立的低权重关键词字段，正式名称及可靠的规范名称保留为名称别名。
2. 对 `of`、`up` 等停用词排除独立命中；`settings`、`setup`、`change` 等高频词仅作辅助证据，不允许单独产生最佳匹配。
3. 数字采用证据分类，不能只依赖长度阈值。缓存还含 `256`、`486`、`1394`；v8 目前仍会保留它们。`1394` 可作为硬件相关关键词，但不应等价于“设备管理器”的名称。
4. 最佳匹配优先要求标题或可靠名称证据；关键词可以帮助召回，不能凭一个宽泛词占据推荐位。

## P1：Windows 设置目录把分类、关联项目和说明混成别名

来源：`src/providers/windows_settings.rs::powertoys_aliases`、`translated_paths`、`merge_results`。

现状：名称、AltNames、父分类、多语言路径、规范名称，以及 Note 文本都进入同一个 `aliases` 数组。合并相同启动目标时还会继续加入其他项目的标题和路径。

实际例子：

- `system` / `系统` 出现在 30 个目录项目中，`privacy` / `隐私` 出现在 29 个项目中。
- 缓存含“设置应用程序 › system”“settings app › 系统”等语言混合的路径，来自每一级路径的跨语言组合。
- “Computer Management”的 38 个别名包含 Task Scheduler、Event Viewer、Device Manager 等子工具；这些子工具又各有自己的入口。
- 颜色筛选器 AltNames 使用 `GreenWeek`、`RedWeek`，对应英文 `Green week` / `Red week`、中文“绿色周”/“红色周”。结合颜色功能语境，这些资源疑似错误，应核对并修正，不能继续扩散成高权重别名。

建议：

- Name 与真正同义的 AltNames 保持高权重；父分类、子工具、Note 分别移入上下文、相关关键词与说明。
- 路径按每种语言分别生成，不生成中英交叉组合；完整路径不作为等价名称。
- 搜索“任务计划程序”时，直接工具入口应优先于“计算机管理”父入口；只有同时输入父级语义时才提高父入口相关性。
- `Microsoft.*` 规范名称可保留用于明确技术查询，避免单个厂商前缀成为最佳匹配证据。

缓存中的英文标题不一定表示界面语言错误：`IndexedSearchEngine` 在返回项目时会调用 `localized_result`。需要区分持久化的英文基准名称与最终显示名称。

## P1：AppsFolder 的包身份不等于应用别名

来源：`src/platform/windows/shell.rs::store_application_with_metadata` 和 `src/providers/app/identity.rs::merge_by_identity`。

实际例子：

- `microsoft sysinternalssuite` 同时作为 27 个应用的别名，包括 Sysinternals Suite、AccessEnum、ADExplorer、ADInsight、Autoruns。
- “入门”和“Windows 备份”共用 `microsoftwindows client cbs`。
- 其他项目有 `60145scottbrogden ditto-cp`、`40174mourinaruto nanazip` 等带发行者数字或包命名的别名。

前一轮已去掉包产品名拆词，但完整包名仍进入强别名，所以这个问题在 v8 仍存在。

建议：AUMID、包家族和发行者放入技术元数据；完整套件名可作为低权重分组关键词。高权重别名优先来自正式显示名称、可信的可执行文件名、历史显示名称和用户手工别名。保留 AUMID 用于身份和启动，不等于必须拿它参与普通名称评分。

## P1：书签的 URL 与容器名称需要分层

来源：`src/providers/dynamic/bookmarks.rs::result`。此项是源码审查，没有抽取用户真实书签。

当前别名直接包括完整 URL、书签文件夹及浏览器配置名称。非空 root 查询会让书签参与统一搜索，因此 `https`、`www`、通用文件夹或配置名称可能让大量无关页面得到强匹配。

建议：标题与用户自定义别名为强证据；规范化域名为中等证据；URL 路径、文件夹及浏览器配置仅辅助筛选。协议和跟踪参数不作为名称证据。保留完整 URL 用于启动，显式 URL 查询仍可精确定位。

## P2：开始菜单、桌面及自定义文件夹

名称主要来自快捷方式或文件名，通常比 Shell 任务关键词可靠，应保留。重点调整少数泛化可执行文件别名：

- `cmd` 对应 6 个命令提示符/VS 开发者环境入口。
- `reaper` 对应 5 个 REAPER 启动变体。
- `uninstall` 对应 3 个不同软件的卸载入口。
- `appverif` 对应 Application Verifier 的主入口、帮助及不同架构入口。

这些是来源级碰撞，现有身份合并可能把其中一些合为多个启动动作，不能直接删除所有同别名条目。应保留 `cmd`、`code` 等有用执行名，对 `uninstall`、`setup`、`helper` 等泛名降权；架构、帮助、重置等词应帮助选择具体启动动作，而不是给主应用引入强烈的无关别名。

自定义目录中的裸 EXE 当前使用文件名作为标题，别名为空。后续可用可信的版本信息 ProductName / FileDescription 改善显示名，保留原始文件名作为执行名别名；不能把完整父路径或发行者无差别加入别名。

## P2：Steam 与其他动态来源

Steam 插件将 appid 放入 `aliases[1]`，同时依赖该位置读取游戏身份。应把 appid 移到专门元数据；标题、官方简称和本地化名称才参与普通文本检索。不要直接删除这个数组元素，否则会破坏现有启动或图标逻辑。短数字保护只覆盖 1～2 位，较长 appid 仍可获得别名精确匹配。

Everything 内置引擎使用后端查询与顺序，文件名和路径具有明确语义，当前不应为文件额外添加父目录、盘符等全局强别名。翻译语言代码和天气入口关键词则有明确交互语境，优先级低于上述来源。

## 同名条目与调整顺序

缓存中还存在跨来源同名项目，如 Task Scheduler、Computer Management、Services、设备管理器。来源不同和标题相同不能证明启动行为相同。应先规范化已知系统工具的启动命令及语义目标，再判断是否合并；深层任务和父页面可能应保留独立入口。

推荐实施顺序：

1. 增加名称别名、关键词、上下文、技术标识的来源与角色，保持旧插件 aliases 的兼容读取。
2. 优先迁移 Shell 任务关键词，加入 `set`、`up`、`settings`、`256`、`486`、`1394` 等回归查询。
3. 调整设置目录的父分类、关联子工具、多语言路径和错误资源词。
4. 清理包身份及书签容器字段的强匹配资格。
5. 最后处理泛化 EXE 别名、启动变体及跨来源语义去重。

下一轮评测应保留代码编辑器、终端、设备管理器、颜色筛选器等真正入口作为困难负例竞争项，并分别检查召回、排序和最佳匹配资格，而不只检查最终是否找到目标。

## 本轮实施范围（2026-11-07）

以上计数描述审查时的 v7 缓存，不代表新索引。当前优化采用通用字段角色，不建立泛词或结果名称黑名单：Shell 关键词、设置关联名称归为关键词，分类与书签容器归为上下文，包身份、URL 和 Steam appid 归为技术标识。高频关键词按候选集合的文档频率识别；数字关键词不能独立成为锚点，数字名称与用户别名仍有效。

本轮不改写翻译资源的具体词条，也不按 EXE 名称惩罚某些应用；泛化执行名、启动变体和跨来源语义去重留待独立验证。缓存版本升级为 v9，运行软件后重建系统索引；旧插件若继续把非名称写入 aliases，仍保留兼容语义，需要由插件迁移到新增字段。

## 本地化名称召回回归

用户反馈 `notepad` 无法召回“记事本”。只读检查实际 v9 缓存确认，该 AppsFolder 记录只有中文标题、空别名以及完整技术标识；此前删除包名拆词后，没有补充可信的非本地化名称来源。完整包标识不能替代应用名称。

真实包清单中，对应应用 ID 的 `Executable` 为 `Notepad\Notepad.exe`。修复方向是按应用 ID 读取包清单的执行名称，作为有来源依据的别名；仍保留原包身份的技术字段角色，不采用具体软件映射，也不恢复对整包名称的无差别拆词。修复需要更新缓存版本，覆盖已经生成的 v9 空别名记录。

已实施上述规则，缓存版本为 v10。本机 Windows 原生集成测试通过：真实 AppsFolder 来源经包清单补充别名后，`SearchCore` 的 `notepad` 查询能召回记事本，原 shell 启动目标保持一致。该验证不代表已经支持任意语言的名称互译；只有实际索引来源提供的显示名与可信执行名会加入名称检索。
