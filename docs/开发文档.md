# Launcher 开发方向

## 1. 项目定位

基于 **Rust + Slint** 开发桌面 Launcher，提供：

* 快速唤起与搜索
* 多数据源统一搜索
* 文件 / 应用 / 命令等内置 Provider
* 第三方插件扩展
* 统一 Result 与 Action
* 基于使用习惯的结果排序

---

## 2. 整体架构与数据流

当前 Phase 1 的实际落地范围是 `Provider -> SearchCore -> ResultRow`：AppProvider 负责应用发现、入口关联、Identity 合并、兜底分类和别名生成；ShortcutProvider 负责动态生成命令和配置型网页快捷指令；WeatherProvider 负责天气关键词和详情结果；SearchCore 负责匹配、合并动态结果与排序；Ranker 负责消费本地使用历史；launcher 负责执行启动动作。Result Aggregator 仍属于后续阶段，插件 IPC 已按短生命周期协议接入。

AppProvider 当前按以下顺序处理 Windows 应用：

```text
AppsFolder / Package / StartMenu / Desktop
    ↓
识别远程 URL，关联文件入口与已发现应用
    ↓
应用记录关联时同步合并 LaunchEntry，并按实际启动行为去重
    ↓
优先使用真实文件目标进行兜底分类
    ↓
刷新默认启动入口、Action 和展示位置
```

分类不能提前到入口关联之前：AppsFolder 常提供 `shell:` 目标，而开始菜单快捷方式可能提供真实 `.exe` 或本地 `.html`；先关联再分类可以避免本地 HTML 被 Shell namespace 误判为 Application。远程 HTTP/HTTPS 入口仍单独排除在应用入口关联之外。

应用记录与启动入口的合并遵循同一套数据流：当两个来源被判断为同一应用时，立即合并来源、别名、图标和启动入口；入口按规范化目标、启动参数和工作目录判断是否具有不同启动行为。来源路径本身只是发现来源，不会单独制造启动入口。

未指定工作目录的本地可执行文件按目标文件所在目录归一化，以便合并 AppsFolder 和快捷方式对同一个 exe 的等价入口；明确不同的参数或工作目录仍会保留为独立入口。虚拟 `shell:AppsFolder\\...` 入口没有真实 exe 时保持保守策略：它可以在受限条件下与同名快捷方式关联为同一应用记录，但不会仅凭标题或 identity 将 Shell 启动行为强制合并到 exe 启动行为。

对于 Windows 中无法通过目标路径直接对应的特殊快捷方式，允许使用受限的标题回退：仅当应用 identity 为 `shell:` 或 `exe:`、快捷方式标题与应用标题完全一致、且快捷方式目标扩展名为 `.exe` 或 Windows 安装器生成的 `.ico` 占位文件时才建立关联。候选应用仍必须唯一；不能通过产品名硬编码或仅凭同名标题合并应用，避免 WSL、Docker Desktop 等特殊入口引入误合并。

默认入口按来源优先级和可执行目标选择。普通点击使用默认入口；上下文菜单只显示其余入口。普通入口以“目标执行文件名 + 参数”的形式展示；`.lnk` 快捷方式则显示快捷方式名称，不展开目标执行文件和参数。入口的快捷方式路径、工作目录和参数仍由对应的 `LaunchEntry` 保存，启动时不会因为展示文本而改变。

搜索结果不设置数量上限。SearchCore 返回全部匹配结果，UI 使用可滚动的 `ListView` 展示；结果文本会先提交到界面，图标只针对当前可见区域在后台异步解析，并通过查询代次校验避免旧查询回填到新结果。图标由 `IconService` 缓存，滚动到新的区域时再按需加载。缓存分为来源字节和最终像素两层：favicon、插件资源和 SVG 源数据可以跨尺寸复用，Windows Shell 固定尺寸图标不因请求尺寸不同重复提取；相同图标的并发解析会合并。搜索框和结果列表统一使用 24px 图标槽位。网页快捷指令按协议、主机和端口缓存 favicon，不会因为查询参数变化重复请求。分页和更细粒度的虚拟化属于后续优化。

图标解析保持源图质量：Windows Shell 原生图标按 32×32 大图标读取；外部 favicon 和插件图片最多缩小到 64×64，但不会把低于 64px 的图标主动插值放大。低分辨率图标保留原始尺寸，避免人为放大造成模糊。

```text
                         Slint UI
                            │
                            ▼
                       Search Core
                            │
                  Provider Selection
                            │
          ┌─────────────────┼─────────────────┐
          ▼                 ▼                 ▼
     App Provider   Shortcut Provider     Plugins
          │                 │                 │
          └─────────────────┼─────────────────┘
                            ▼
                   Candidate Retrieval
                            │
                            ▼
                     Fuzzy Matching
                            │
                            ▼
                          Ranker
                            │
                            ▼
                  Result Aggregator
                            │
                            ▼
                       ViewModel
                            │
                            ▼
                        Slint UI
                            │
                            ▼
                    Action Execution
```

核心原则：

> **Provider 负责提供数据，Search Core 负责搜索流程，Ranker 负责排序，Result 负责统一数据表达，Action 负责执行，Slint 负责展示与交互。**

## 3. Provider

所有数据源统一抽象为 Provider：

```text
App
File
Command
Bookmark
Calculator
GitHub
Spotify
...
```

Provider 可以分为：

* **Indexed Provider**：拥有本地索引
* **Dynamic Provider**：查询时动态获取
* **Action Provider**：主要提供命令 / Action

当前已实现 `ShortcutProvider` 这一类 Dynamic / Action Provider：内置 `>` 命令快捷指令、内置 `w` 网址快捷指令，以及通过配置文件定义的 URL 模板快捷指令。天气由独立的 `WeatherProvider` 处理，作为本地化关键词或其模糊匹配触发的详情结果，不参与 shortcut 的动作语义。`w` 支持显式输入前缀，也会识别明显的 HTTP/HTTPS 网址并生成高优先级的默认浏览器打开动作。

模糊搜索候选由 ProviderRegistry 统一收集，Provider 只需声明 `supports_fuzzy_search()` 并提供候选项；实际匹配算法和 `fuzzy_search` 配置由 SearchCore 统一处理。

### 3.1 Windows 设置 Provider 计划

Windows 设置页不提供公开的运行时枚举 API。设置入口使用 `ms-settings:` URI，但页面是否可用会随 Windows 版本、SKU、硬件和系统策略变化。因此不把设置 URI 直接硬编码在 Rust Provider 中，也不依赖用户安装 PowerToys。

后续恢复 Windows 设置 Provider 时，以上游数据同步为准：

* 使用 Microsoft PowerToys Windows Settings 插件的 `WindowsSettings.json` 作为主要上游清单；该项目维护设置名称、URI、区域、别名以及引入/废弃 Build 信息。
* 使用 Flow Launcher Windows Settings 插件作为辅助校验来源，不作为运行时依赖。
* 在构建阶段同步并转换为 wowie 自己的轻量数据格式，保留 MIT License attribution。
* 运行时仅负责读取本地清单，并依据 Windows Build、硬件能力和其他条件过滤条目。
* 明确废弃或无法确认可用性的页面默认不进入索引；`ms-settings:` 根入口作为兜底。

该方案避免联网查询、PowerToys/.NET 运行时依赖和重复维护完整设置列表，同时保留 wowie 自己的中文标题、别名和排序覆盖能力。数据同步脚本和清单接入属于后续工作，当前版本不提供 Windows 设置索引。

### 3.2 Provider 自动注册约定

动态 Provider 和详情 Provider 按目录自动发现，不在 `SearchCore`、`main.rs` 或注册表中维护具体类型列表：

* 查询型 Provider 放在 `src/providers/dynamic/*.rs`，实现 `DynamicProvider`，并提供 `register(registry, shortcuts)` 函数。
* 详情 Provider 放在 `src/details/*.rs`，实现 `DynamicDetailProvider`，并提供 `register(registry)` 函数。
* `build.rs` 扫描这两个目录中的 `.rs` 文件（排除 `mod.rs`），生成模块声明和 `register_all`；文件名必须是合法的 Rust snake_case 模块名。
* 配置变更和语言变更通过 trait 的默认钩子广播；不需要配置或语言的 Provider 不必覆盖 `replace_config` / `set_language`。
* Provider 的 `query` 运行在搜索线程，不得触碰 Slint UI；网络和其他慢操作应放入详情加载或独立工作线程。

AppProvider 内部的 Windows 发现来源仍属于同一个索引 Provider，由 `app.rs` 统一编排；来源发现、文件/URL 解析和 Provider 诊断位于 `src/providers/app/discovery.rs`，入口关联和启动行为规则位于 `src/providers/app/association.rs`，Identity、路径归一化和合并规则位于 `src/providers/app/identity.rs`。新增独立动态 Provider 不应修改 AppProvider。

应用入口保持轻量：`src/main.rs` 只负责声明顶层模块并调用 `ui::run()`；Launcher 的 Slint 类型、窗口生命周期、事件绑定、详情模型、结果模型和上下文动作分别维护在 `src/ui/` 下。详情 Provider 和数据加载仍位于 `src/details/`，不与 UI 展示层混合。搜索核心与领域模型位于 `src/core/`，图标解析和启动行为等运行时服务位于 `src/services/`。通用的 HTTP 客户端和本地化查询位于 `src/utils/http.rs` 与 `src/utils/i18n.rs`，新增与具体业务无关的共享工具应优先放入 `src/utils/`。

#### 新增动态 Provider

以 `src/providers/dynamic/example.rs` 为例：

```rust
use crate::{
    config::ShortcutConfig,
    provider::{DynamicProvider, ProviderRegistry},
    result::SearchResult,
};

pub fn register(registry: &mut ProviderRegistry, _shortcuts: Vec<ShortcutConfig>) {
    registry.register(ExampleProvider::new());
}

impl DynamicProvider for ExampleProvider {
    fn query(&self, query: &str) -> Vec<SearchResult> {
        // 只生成统一 SearchResult，不更新 UI。
        let _ = query;
        Vec::new()
    }
}
```

新增该文件后直接编译即可接入；不需要修改 `provider.rs`、`providers/mod.rs`、`search.rs` 或 `main.rs`。Provider 自己负责稳定的 `id` / `identity`、分类、别名、图标和 Action。

#### 新增详情 Provider

详情模块遵循同样的自动发现规则。`register` 中构造 Provider 并注册到 `DetailRegistry`；`matches` 只判断结果归属，`cached` 返回已有数据，`load` 执行慢操作，`error_view` 返回可展示的失败状态。详情加载由 UI 线程外执行，完成后通过查询/选中代次校验再回填。

## 4. Result 与 Action

不同 Provider 的原始数据结构可以完全不同，但最终转换成统一 Result：

```text
Source Item
    ↓
Search Document
    ↓
Search Result
    ↓
Display Result
```

Result 至少包含：

```text
Result
├── Identity
├── Presentation
├── Search Information
├── Ranking Information
└── Actions
```

例如文件可以提供：

```text
Open
Copy Path
Open Folder
Rename
Delete
```

Result 描述“是什么”，Action 描述“能做什么”。

快捷指令使用独立的 `ResultCategory::Shortcut`，不经过普通文件或应用分类器；可执行快捷指令通过统一的 `Action::Launch` 执行。动态详情结果由对应的 Provider 生成，并由 UI 根据选中结果打开 Detail View。

### 4.1 快捷指令配置

快捷指令配置位于用户配置文件的 `shortcuts` 数组。读取配置时，前缀会规范为末尾带一个空格的字面量，因此 `g` 会按 `g ` 参与匹配，避免误匹配 `git` 等普通关键词：

```json
{
  "name": "Search with Google",
  "prefix": "g",
  "template": "https://www.google.com/search?q={query}"
}
```

`{query}` 会被替换为 URL 编码后的用户输入。输入 `g rust lang` 可打开对应搜索页面。内置 `> command` 不需要写入配置；无前缀输入时快捷指令通过意图优先级作为低优先级兜底结果，不再依赖额外的负 `ranking_bias`。

配置快捷指令由现有 `ShortcutProvider` 自动读取，支持三种 `type`：

* `url`：使用 `template`，其中 `{query}` 会进行 URL 编码；
* `application`：使用 `target` 启动程序，使用 `arguments` 传递未编码参数；
* `command`：使用 `target` 和 `arguments` 组合命令，并通过 PowerShell 执行。

例如应用和命令快捷指令：

```json
[
  {
    "name": "Open Notes",
    "prefix": "n",
    "type": "application",
    "target": "C:/Tools/notes.exe",
    "arguments": "{query}"
  },
  {
    "name": "Run Git Status",
    "prefix": "gs",
    "type": "command",
    "target": "git",
    "arguments": "status --short"
  }
]
```

新增配置型快捷指令只需要修改配置文件，不需要修改 Rust 代码或注册 Provider。配置文件 watcher 会热加载快捷指令；如果修改的是内置 `>`、`w` 或应用型快捷指令，则修改 `src/providers/dynamic/shortcut/` 下对应的实现文件；天气行为位于 `src/providers/dynamic/weather.rs`。`shortcut.rs` 只负责快捷指令统一调度，不需要在其他文件重复注册。

内置 `w` 快捷指令用于打开网址：输入 `w example.com/path` 会打开 `https://example.com/path`。快捷指令解析按前缀字面量匹配，是否包含空格由前缀本身决定；内置命令和网址前缀分别是 `> ` 与 `w `。网址识别统一使用成熟的 `linkify` 库：它负责从输入中定位 URL、处理可选协议以及边界标点；无协议输入的识别范围完全以 `linkify` 的能力为准，不再由 Launcher 为 `localhost`、裸 IP 或其他特殊主机增加额外规则。识别出的无协议 URL 会按 `https://` 打开；带有非 HTTP/HTTPS 协议的结果不会生成网页快捷指令。显式输入 `w` 后即使参数未通过网址识别，也保留统一的“打开网址”动作并按 `https://` 处理。`w` 的预览和网址结果只使用系统默认浏览器图标，不请求目标站点的 favicon；已配置的可信 URL 快捷指令才允许继续使用 favicon 获取逻辑。

执行命令优先使用 PowerShell 7（`pwsh.exe`），找不到时使用 Windows PowerShell（`powershell.exe`），并由 Windows 的默认终端承载。快捷指令的展示分类为“Shortcut / 快捷指令”。

Rust 侧 i18n 使用统一的 `i18n::tr(language, message_id)` 查找普通文本，构建阶段由 `build.rs` 一次解析全部 PO 条目并生成包含 `locale`、`msgctxt`、`msgid` 和 `msgstr` 的静态表；新增普通翻译无需修改 Rust 代码。需要多个搜索词时使用 `i18n::tr_list()`，在 PO 的 `msgstr` 中用 `|` 分隔；需要兼容本地语言和默认英语时使用 `i18n::tr_aliases()`，它会自动读取当前语言与 `en` 的对应词条并去重。天气 Provider 使用 `Weather keyword` 词条，英文输入 `weather`、简体中文输入 `天气` 及其模糊匹配都会生成同一个稳定结果 `weather:current`，其路径显示使用 PO 中的 `View weather information`。

天气结果由独立的 `WeatherProvider` 生成，是本地化关键词或其模糊匹配触发的详情结果，不参与 shortcut 的结果隔离、搜索框图标替换和显式 shortcut 意图优先级；最终结果仍由 SearchCore 的通用匹配流程和 `fuzzy_search` 配置过滤。选中后由 UI 线程外的 `src/details/weather.rs` 获取 IP 粗略位置，并请求天气服务。结果通过查询/选中代次校验后回填详情面板。面板展示温度、天气状况、湿度、风速、数据来源和基于 WMO weather code 的彩色图形。天气图标由 `IconService` 内置绘制，不依赖外部文件。

详情面板已抽象为统一的声明式 `DetailView`。`SearchResult` 可以提供标题、摘要、来源、文本/指标/图标/天气图形/间距块以及最多三个受限操作；插件通过 JSON Lines 的 `detail` 字段提供同一结构，UI 不接受插件注入的 Slint 代码或任意控件。详情面板按内容数量自动增高，可额外声明最小高度而非固定高度；列表列仍按自身内容决定高度，不会被详情面板挤压。插件详情最多渲染十个块。天气只是其中一个 Provider 实现，仍由 `src/details/weather.rs` 负责异步数据获取。

所有 HTTP/HTTPS 访问统一使用共享的 Rust `reqwest` 客户端（`src/utils/http.rs`），统一设置连接/请求超时；favicon、IP 定位和天气请求不得通过 `curl.exe`、PowerShell Web cmdlet 或其他外部网络程序实现。Windows 平台的外部进程只能用于明确的平台兼容能力，且必须设置 `CREATE_NO_WINDOW`，避免 Release GUI 应用弹出控制台或抢走焦点。

配置还提供 `show_advanced_details` 开关，默认关闭。普通模式下，应用位置显示最终运行程序名以及默认入口参数，不显示完整目录；控制面板位置继续隐藏，AppsFolder 等技术标识不会直接暴露。开启后显示默认入口解析出的完整目标路径和参数。该开关只影响 UI 展示，不影响默认入口、启动行为和搜索。

配置文件变化统一通过同一个 watcher 触发，并在运行时应用到对应的平台、Provider、搜索和 UI 状态。热键会先注销旧注册再注册新值；窗口宽度、主题、失焦隐藏、语言、快捷指令、插件 locale、Provider 和高级详情均支持热重载。`renderer` 属于窗口后端选择，默认使用 `femtovg`，也支持 `skia`、`skia-opengl` 和 `software`；其中 `skia` 会兼容映射到当前编译的 OpenGL Skia 后端。`show_on_startup` 只描述进程启动时行为，这两项保持启动期生效，修改后需重启应用。

上下文菜单中的普通操作与其他启动入口分组显示。只有存在非默认入口时才显示本地化的“Other launch entries / 其他启动入口”分组标题；普通启动入口显示执行文件名和参数，`.lnk` 快捷方式显示快捷方式名称，即使开启高级详情也不会在菜单中展开完整路径。

配置还提供 `show_advanced_launch_entries` 开关，默认关闭。关闭时“其他启动入口”仅显示参数不同的快捷方式（例如 Chrome 的不同 profile）；开启后显示除主入口外所有可启动的已索引入口，Windows 安装器生成的 `.ico` 占位目标仍不会显示。该开关支持配置文件热加载，不影响默认入口和启动行为。

## 5. 插件

插件采用分层演进架构：

> **第一阶段：独立进程 + JSON Lines IPC；目标架构：宿主内嵌 Lua 虚拟机 + Lua API**

```text
Launcher Core
      │
      │ IPC
      ▼
Plugin Process
```

当前已接入的短生命周期协议：

```text
query
execute
```

`initialize`、`cancel`、`shutdown` 属于常驻 Provider 协议，仍需补齐生命周期管理和查询取消语义。

当前第一版插件通过 Manifest 发现，使用 `runtime + entry_point` 启动外部脚本进程。Lua、Python、Node 或其他可执行程序都可以实现同一协议；其中 Lua 运行时由插件外部提供，因此不保证用户环境无依赖。查询请求携带 `locale` 和 `fallback_locale`，插件自行管理业务文案的 `locales/` 目录。Windows Release 构建中插件 query / execute 子进程必须设置 `CREATE_NO_WINDOW`；插件查询可能在每次输入时触发，不能让控制台窗口抢占 Launcher 焦点。短生命周期插件的 query / execute 共享统一的进程启动与 stdout 读取路径。

当前 Query / Execute 为短生命周期进程模式：每次查询或执行都会启动一个插件进程，完成后退出。该模式优先保证协议简单、运行时可替换和故障隔离。

常驻进程模式已接入基础的 `initialize`、`query` 和 `execute` 请求，尤其适用于需要增量索引的插件；完整的取消、增量索引、进度和优雅退出生命周期仍属于后续工作。常驻模式不是最终的 Lua 方案，而是现有外部进程协议的过渡形态：

```text
Plugin Process
    │
    ├── initialize
    ├── index / rebuild
    ├── update
    ├── query
    ├── execute
    ├── cancel
    └── shutdown
```

常驻 Provider 需要维护自己的索引状态，并通过文件、数据库、第三方服务事件或定时同步接收增量更新。Launcher 只消费统一的 Item / Result，不直接了解插件内部索引实现。

后续协议需要补充：

* `query_id`：避免旧查询覆盖新查询
* `cancel`：取消正在执行的查询
* `revision` 或 `cursor`：标识索引版本和增量位置
* `upsert` / `remove`：传递增量变更
* `ready` / `progress`：报告索引初始化进度

插件通过 Manifest 注册：

```text
id
name
version
api_version
entry_point
keywords
permissions
```

插件可以使用 Lua、Python、Node、Rust、C# 等语言实现。

### 5.1 目标：mpv 式内嵌 Lua 插件

参考 mpv 的 Lua 脚本架构，wowie 最终将把 Lua 虚拟机直接编译进 Launcher。插件加载后与 Launcher 共用进程，但使用独立的 Lua 状态、错误边界和插件上下文；用户只需安装插件文件，不需要额外安装 Lua、Python 或 Node。

```text
Launcher Process
    ├── Search Core / Result / Action
    ├── Embedded Lua VM
    │     └── wowie Lua API
    └── plugins/<id>/main.lua
```

Lua 插件只负责业务逻辑，平台能力由宿主 API 提供。例如 Everything 插件通过 `wowie.everything.search(query)` 请求文件结果，由 Rust 宿主负责 Windows IPC、线程、超时和错误隔离。Lua 插件不得直接依赖外部命令、PowerShell 或用户安装的脚本运行时。

目标 API 方向：

* `wowie.result(...)`：创建统一 SearchResult。
* `wowie.action(...)`：声明插件 Action。
* `wowie.on("query", handler)`：处理查询。
* `wowie.on("execute", handler)`：处理 Action 执行。
* `wowie.everything.search(query)`：调用 Everything 本地 IPC。
* `wowie.locale(...)`：读取插件本地化消息。

内嵌 Lua 与 JSON Lines 插件共存：原生或受信任插件优先使用内嵌 Lua；第三方插件仍可使用外部进程协议。宿主必须限制单次回调耗时、捕获 Lua 错误、支持插件禁用，并在应用退出时释放 Lua 状态。Lua API 只暴露稳定的宿主能力，不把 Slint、Windows HWND 或内部 Rust 类型直接暴露给插件。

### Phase 5 — Ranking

当前已实现第一版本地智能排序：

* `SearchCore` 保持匹配分为主要排序依据，`Ranker` 只提供有限的行为加分。
* 排序使用结构化 `RankKey`：匹配等级 > 匹配质量 > 行为分 > Provider 偏置 > 标题 > 稳定 ID；行为分不会跨越精确、前缀和包含等匹配等级。
* 快捷指令按用户意图分层：显式前缀（如 `> command`、`g query`）优先，普通应用结果居中，无前缀生成的隐式快捷指令仅作为低优先级兜底结果；该分层由 `intent_priority` 实现，不使用负 `ranking_bias`。
* 输入快捷指令前缀和空格后立即显示显式快捷指令的预览项，例如 `> ` 显示“执行命令”；预览项不可执行，继续输入参数后才生成实际 Action。
* 记录稳定 `result_id` 的成功执行次数和最近执行时间。
* 同时保存项目级使用记录与 `query + result_id` 级使用记录。
* 使用 7 天半衰期计算 Frecency，最多保留有限行为加分，避免历史记录压过明确匹配。
* 普通启动成功或插件 `execute` 成功后才记录；选中、滚动和打开上下文菜单不记录。
* 排序历史独立保存到配置目录的 `history.json`，不写入 `config.json`，损坏时自动从空历史开始。

搜索支持通过配置文件中的 `fuzzy_search` 开关控制，默认开启。搜索等级保持为：精确匹配 > 前缀匹配 > 包含匹配 > 模糊匹配；关闭后只保留前三种匹配。模糊匹配使用 `nucleo-matcher`，仅对标题和别名匹配，不搜索路径或启动目标，避免引入噪声。模糊匹配的使用分数仍不能跨越明确的匹配等级，也不会改变快捷指令的意图优先级。

后续可增加显式置顶、降低排序、清除单条记录、清除全部历史和插件禁用自动排序等用户控制。空查询的最近使用结果仍属于后续 UI/History 设计，当前查询为空时不返回普通搜索结果。

## 8. 开发原则

### 8.1 Phase 1 平台生命周期评估

Windows 全局热键使用原生 `RegisterHotKey`，由 `PlatformIntegration` 在后台线程运行消息循环，并通过 `PlatformEvent` 转发到 Slint UI 线程。窗口的显示、隐藏、激活、定位和失焦监听同样只通过该边界访问平台 API；窗口本身保持常驻，隐藏时不退出事件循环。该方案避免把 Windows HWND、热键消息和 DWM 细节泄漏到 Launcher 核心，当前阶段无需额外引入热键依赖。

热键线程目前随进程退出而结束；应用没有“退出”操作，因此不需要主动注销热键。若后续加入退出或热键重载，应增加线程停止信号，并在消息循环结束前调用 `UnregisterHotKey`。

Windows 托盘和单实例控制属于 `PlatformIntegration` 边界：托盘左键转换为显示 Launcher 事件，右键菜单只提供本地化的退出动作；release 构建通过命名互斥体阻止同一应用多开，debug 构建保留多开能力以便开发调试。应用图标作为 Windows 资源嵌入，不依赖运行时工作目录。

平台规则和跨 Provider 的协议处理应优先提取到公共 helper：例如 Shell namespace 判断、插件 Action 定位和 Windows 图标像素读取。Windows 平台实现按职责维护：`src/platform/windows/icons.rs` 负责图标与默认关联图标，`src/platform/windows/shortcuts.rs` 负责 ShellLink 快捷方式解析，`src/platform/windows/com.rs` 提供共享 COM 生命周期工具，`windows.rs` 保留平台生命周期、来源发现和系统集成编排。核心模块已按职责归入 `src/core/` 与 `src/services/`，后续拆分应以降低耦合为目标，不应仅为缩短文件长度扩大行为变更范围。

### 自定义快捷命令类型

`shortcuts` 保留原有 URL 模板格式。每项可通过 `type` 指定为 `url`、`application` 或 `command`；省略 `type` 时按 `url` 处理，以兼容旧配置。

应用快捷命令使用 `target` 指定程序，使用 `arguments` 指定参数；命令快捷命令使用同样的字段，并通过系统 Shell 执行。`{query}` 在应用和命令参数中按原始文本替换，在 URL 模板中继续使用 URL 编码替换。

```json
{
  "name": "Open in Notepad",
  "prefix": "n",
  "type": "application",
  "target": "notepad.exe",
  "arguments": "{query}"
}
```

```json
{
  "name": "Git status",
  "prefix": "gs",
  "type": "command",
  "target": "git",
  "arguments": "status --short {query}"
}
```

最终目标：

> **构建一个以统一 Result 为核心、能够接入不同数据源和插件的桌面搜索平台。**
