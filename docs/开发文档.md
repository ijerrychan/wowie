# Launcher 开发方向

## 1. 项目定位

基于 **Rust + Slint** 开发桌面 Launcher，提供：

* 快速唤起与搜索
* 多数据源统一搜索
* 文件 / 应用 / 命令等内置 Provider
* 第三方插件扩展
* 统一 Result 与 Action
* 基于使用习惯的结果排序

---

## 2. 整体架构与数据流

当前 Phase 1 的实际落地范围是 `AppProvider -> SearchCore -> ResultRow`：Provider 负责发现、Identity 合并和别名生成，SearchCore 负责模糊匹配与排序，launcher 负责执行启动动作。独立 Ranker、Result Aggregator 和插件 IPC 仍属于后续阶段。

```text
                         Slint UI
                            │
                            ▼
                       Search Core
                            │
                  Provider Selection
                            │
          ┌─────────────────┼─────────────────┐
          ▼                 ▼                 ▼
     App Provider      File Provider       Plugins
          │                 │                 │
          └─────────────────┼─────────────────┘
                            ▼
                   Candidate Retrieval
                            │
                            ▼
                     Fuzzy Matching
                            │
                            ▼
                          Ranker
                            │
                            ▼
                  Result Aggregator
                            │
                            ▼
                       ViewModel
                            │
                            ▼
                        Slint UI
                            │
                            ▼
                    Action Execution
```

核心原则：

> **Provider 负责提供数据，Search Core 负责搜索流程，Ranker 负责排序，Result 负责统一数据表达，Action 负责执行，Slint 负责展示与交互。**

---

## 3. Provider

所有数据源统一抽象为 Provider：

```text
App
File
Command
Bookmark
Calculator
GitHub
Spotify
...
```

Provider 可以分为：

* **Indexed Provider**：拥有本地索引
* **Dynamic Provider**：查询时动态获取
* **Action Provider**：主要提供命令 / Action

---

## 4. Result 与 Action

不同 Provider 的原始数据结构可以完全不同，但最终转换成统一 Result：

```text
Source Item
    ↓
Search Document
    ↓
Search Result
    ↓
Display Result
```

Result 至少包含：

```text
Result
├── Identity
├── Presentation
├── Search Information
├── Ranking Information
└── Actions
```

例如文件可以提供：

```text
Open
Copy Path
Open Folder
Rename
Delete
```

Result 描述“是什么”，Action 描述“能做什么”。

## 5. 插件

插件采用：

> **独立进程 + JSON Lines IPC**

```text
Launcher Core
      │
      │ IPC
      ▼
Plugin Process
```

当前短生命周期协议：

```text
query
execute
```

`initialize`、`cancel`、`shutdown` 属于后续常驻进程协议，目前尚未接入。

当前第一版插件通过 Manifest 发现，使用 `runtime + entry_point` 启动外部脚本进程。Lua、Python、Node 或其他可执行程序都可以实现同一协议。查询请求携带 `locale` 和 `fallback_locale`，插件自行管理业务文案的 `locales/` 目录。

当前 Query / Execute 为短生命周期进程模式：每次查询或执行都会启动一个插件进程，完成后退出。该模式优先保证协议简单、运行时可替换和故障隔离。

常驻进程属于后续 Provider 能力，尤其适用于需要增量索引的插件：

```text
Plugin Process
    │
    ├── initialize
    ├── index / rebuild
    ├── update
    ├── query
    ├── execute
    ├── cancel
    └── shutdown
```

常驻 Provider 需要维护自己的索引状态，并通过文件、数据库、第三方服务事件或定时同步接收增量更新。Launcher 只消费统一的 Item / Result，不直接了解插件内部索引实现。

后续协议需要补充：

* `query_id`：避免旧查询覆盖新查询
* `cancel`：取消正在执行的查询
* `revision` 或 `cursor`：标识索引版本和增量位置
* `upsert` / `remove`：传递增量变更
* `ready` / `progress`：报告索引初始化进度

插件通过 Manifest 注册：

```text
id
name
version
api_version
entry_point
keywords
permissions
```

插件可以使用 Lua、Python、Node、Rust、C# 等语言实现。

## 6. 文件搜索

文件搜索作为第一个核心 Indexed Provider：

```text
Filesystem
    ↓
Indexer
    ↓
Local Index
    ↓
File Provider
```

索引更新采用：

* Initial Scan
* Filesystem Events
* Periodic Reconciliation

文件名 / 路径搜索与全文搜索分开，全文搜索暂不作为第一阶段重点。

---

## 7. 开发阶段

### Phase 1 — Launcher

实现 Hotkey、UI、Search Core、App Provider、Result、Launch。

### Phase 2 — File Search

加入 Indexer、Local Index、File Provider、Filesystem Watcher、Fuzzy Search。

### Phase 3 — Provider

统一 Provider / Result / Action 接口，增加 Calculator、Command、Bookmark 等 Provider。

### Phase 4 — Plugin

当前已实现：

* Plugin Manager
* Manifest 发现
* 外部脚本进程
* JSON Lines IPC
* Query / Result / Execute 协议
* 插件自带 locales 与 locale fallback

后续实现：

* 常驻插件进程
* query_id / cancel
* 增量索引与 Provider 生命周期
* Action 菜单、List / Detail / Form View
* 权限和沙箱

### Phase 5 — Ranking

加入 History、Recency、Frequency、Frecency 等排序因素。

## 8. 开发原则

### 8.1 Phase 1 平台生命周期评估

Windows 全局热键使用原生 `RegisterHotKey`，由 `PlatformIntegration` 在后台线程运行消息循环，并通过 `PlatformEvent` 转发到 Slint UI 线程。窗口的显示、隐藏、激活、定位和失焦监听同样只通过该边界访问平台 API；窗口本身保持常驻，隐藏时不退出事件循环。该方案避免把 Windows HWND、热键消息和 DWM 细节泄漏到 Launcher 核心，当前阶段无需额外引入热键依赖。

热键线程目前随进程退出而结束；应用没有“退出”操作，因此不需要主动注销热键。若后续加入退出或热键重载，应增加线程停止信号，并在消息循环结束前调用 `UnregisterHotKey`。

优先确定**核心抽象**，不要过早锁死具体实现。

核心抽象：

```text
Provider
SourceItem
SearchDocument
SearchResult
DisplayResult
Action
Plugin
Query
```

暂时不锁死：

```text
Database
Search Engine
IPC Format
Filesystem Watcher
Ranking Algorithm
Plugin Sandbox
```

最终目标：

> **构建一个以统一 Result 为核心、能够接入不同数据源和插件的桌面搜索平台。**
