# 索引来源精简与名称补全方案

日期：2026-11-07。目标：减少重复扫描和低价值强匹配信息，保留实际应用、启动变体及可信名称；不按软件名称或 ID 特判。

## 审计依据

只读检查本机 v10 缓存，原始来源统计如下。独有身份表示该缓存其他来源没有相同 identity，不等于最终合并后的独有应用数；不同启动参数也不能仅凭同名合并。

| 来源 | 原始记录 | 不重复 identity | 其他来源没有的 identity |
| --- | ---: | ---: | ---: |
| AppsFolder | 178 | 178 | 115 |
| PackagedApps | 0 | 0 | 0 |
| StartMenu | 128 | 110 | 46 |
| Desktop | 16 | 16 | 13 |
| ControlPanel | 431 | 431 | 431 |

控制面板来源包含设置目录补充项，不能将此表理解为全部来自 Shell。CustomDirectories 在该缓存中未出现。包枚举为空可能受运行环境、权限或系统状态影响，不能据此删除包枚举能力。完整性以来源合并后的身份与启动行为集合为准。

本机桌面原生审计同样观察到 Package 结果为 0，尚未定位具体原因；这不表示本机没有已安装包。现有发现接口在多个 API 失败点直接返回空集合，后续应区分“成功且为空”和“枚举／应用列表读取失败”，记录阶段与错误计数，使补缺失败可以诊断。当前保留该发现能力，不将空集合当成来源冗余的证据。

## 来源决策

| 来源或信息 | 决策 | 原因 |
| --- | --- | --- |
| AppsFolder + Package | 合为一个逻辑应用来源；内部保留两条发现渠道并按身份合并 | 精简调度、缓存和更新入口，保留 Package 独有条目、名称与包元数据 |
| StartMenu | 保留 | 有独有应用、快捷方式参数、工作目录和图标；不能由 AppsFolder 完整替代 |
| Desktop | 保留 | 有用户自建入口与独有记录 |
| CustomDirectories | 保留为用户明确配置的补缺渠道 | 便携软件和自选文件无法依赖系统注册 |
| Shell 控制面板 + 设置目录 | 保留并按实际启动目标合并 | Shell 提供本机安装状态；目录提供设置页与多语言名称，职责互补 |
| Everything / Windows Search | 继续使用既有文件搜索后端 | 避免把全盘文件、父路径、盘符复制为应用强别名 |
| 插件 manifest / command keywords | 从通用结果强别名中收敛 | 引擎入口词不是每条插件结果的等价名称 |
| 插件 requested_query 自动别名 | 移除自动拼接；显式 session 交互需独立兼容 | 任意查询变成结果自身别名会制造精确匹配 |
| 包发行者、版本、哈希、整包名拆词 | 不作为强名称补全 | 无法证明其等价于具体应用 |

合并来源不等于只在主来源失败时才枚举补充来源：后者可能遗漏主来源未包含的单个应用。新增元数据不能覆盖正确的 Shell 启动目标，也不能把同名不同参数的入口删除。

实施审查补充：两路原始记录放入同一逻辑来源后，仍先走原有快捷方式关联，再按 identity 去重。不能提前丢掉 Package 的不同语言 title，仅在 aliases 中保留该词不保证原有严格关联判断还能成立；也不能因此把关联规则放宽为“同名就合并”。保留内部来源证据，最终只产出规范化后的结果。

## 名称缺口的解决路线

### Windows 应用

已经实现：当前 Shell 显示名、快捷方式执行名、同一身份的其他来源名称、按 Application Id 对应的独有 manifest Executable 名称。

本轮评估补充：复用版本资源读取，收集文件自身提供的语言表。FileDescription 是文件描述，可用于弱关键词；ProductName 可能只是套件或操作系统名，不能无条件升级为强别名。仅增加辅助元数据时保持原显示标题不变，避免把安装器、帮助程序误称为主产品。

只读检查本机系统文件也确认了这一点：notepad.exe、cmd.exe、powershell.exe 的 FileDescription 各不相同，但 ProductName 都是 Microsoft Windows Operating System。因此，本轮不把 ProductName 或 OriginalFilename 自动升级成强名称别名；执行名与已验证的 manifest 名称继续承担强名称补全。

后续多语言精确名称：只定位对应 Application 的 DisplayName / ShortName 资源；用明确语言上下文解析 PRI，收集实际存在的本地化名称作为别名。不能把 ms-resource 原文、资源键、包级 DisplayName 或全包字符串表直接加入别名。Windows App SDK MRT Core 支持指定 PRI 和语言上下文，但引入运行时依赖、split/resource package 与语言回退处理之前，必须有原生验证，不在基础路径上猜译名。

官方依据：

- [VERSIONINFO 字段语义](https://learn.microsoft.com/en-us/windows/win32/menurc/versioninfo-resource)
- [VerQueryValue 的语言/代码页表](https://learn.microsoft.com/en-us/windows/win32/api/winver/nf-winver-verqueryvaluew)
- [Manifest 的本地化资源引用](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/mrtcore/localize-strings)
- [MrmCreateResourceManager](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/win32/mrm/nf-mrm-mrmcreateresourcemanager)
- [MrmLoadStringResource](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/win32/mrm/nf-mrm-mrmloadstringresource)

### Steam 游戏

保留本地 appmanifest 名称和 appid 精确身份。发布者可以配置本地化应用名称，但这并不等于启动器可用一个稳定、无需密钥的官方接口取得每个已安装游戏的全部译名。

研究结论：官方 IStoreService/GetAppList 需要 API key，文档的 have_description_language 是描述语言过滤，并未提供每个 appid 的多语言名称集合；旧 ISteamApps/GetAppList 已弃用。不能用该接口的参数名称推断多语言支持，也不将未文档化的商店 appdetails 设为可靠性基础。

可行的后续独立方案：按 appid 为主键维护可审核的用户别名；或者实现可选、可失效的名称补全适配器，仅增强已安装游戏，不枚举全商店，采用后台更新和本地缓存，返回结构和身份验证失败时保留本地名称。若采用本地 appinfo 缓存，需要先完成格式版本、损坏输入和资源上限验证，不能将二进制解析结果无条件作为可信名称。

官方依据：

- [Steam 本地化应用名称](https://partner.steamgames.com/doc/store/localization#localized_app_names)
- [IStoreService/GetAppList](https://partner.steamgames.com/doc/webapi/IStoreService)
- [旧 ISteamApps/GetAppList 弃用说明](https://partner.steamgames.com/doc/webapi/ISteamApps)

### 设置目录和用户自定义名称

设置目录的 Name 与 AltNames 必须继续分角色；其翻译质量问题应修正在资源数据，而不是给排序器增加特例。后续数据审查应报告未解析资源键、多条目同译名、关联工具名被误列为主名称，以及不同启动命令的同名碰撞。通过可审核的资源修正恢复真实名称，不把所有关联工具重新升级为别名。

对厂商没有提供的译名、社区简称，跨软件／跨游戏的用户别名能力是可控补充：按稳定结果 identity 绑定，保存原输入与来源，允许编辑删除；不能让模型猜测的软件译名直接写入可信索引。本轮不新增这套配置 UI，避免把来源精简扩大成新的设置体系。

## 验收

1. 用虚构数据验证：统一来源前后 identity、启动目标、参数、工作目录集合一致；保留包独有应用和同身份的辅助信息。
2. 桌面环境只读运行原生来源覆盖审计，只输出计数，不打印用户应用、路径或书签内容。
3. 插件入口仍可通过声明触发词进入；普通结果不能靠宿主附加的当前查询自动变成精确名称。
4. 保留跨语言记事本原生回归及既有数字关键词回归，不改固定评测的查询和期望来制造改善。
5. 更新缓存版本；fmt、完整测试及差异检查通过后记录实测结果。真实数据的零覆盖损失只能证明本机观察范围，不能宣称所有 Windows 安装环境绝对完整。

## 本轮结果

三项基础改动已完成：统一应用逻辑来源、收敛插件自动强别名、增加有界 EXE 版本辅助元数据。缓存版本为 v11。Windows PRI 完整多语言名称、Steam 名称适配器、用户别名管理，以及 Package 空结果的分阶段诊断属于后续方案，不计作已实现。

2026-11-07，桌面环境串行运行只读来源审计，原始记录：AppsFolder 178、Package 0、StartMenu 128（110 个不重复身份）、Desktop 16、ControlPanel 431、CustomDirectories 0。使用同一份扫描记录，旧流程与统一来源流程最终均为 637 条结果；按 identity 比较完整序列化结果，missing=0、changed=0、added=0。因此本机本次观察范围内，名称、辅助字段及启动证据全部保留；本次没有配置自定义目录，不能把该项零计数当成全局无独有覆盖。

原生 `notepad`→记事本的完整召回与原启动目标检查通过。完整测试 284 通过、0 失败、13 忽略，包含真实系统 EXE 的版本描述读取验证；fmt 和差异检查通过。固定合成评测 25 个正例，Top1/Recall@5/MRR 均为 0.960，负例误返回 0，最佳匹配预期 2/2。该指标只用于回归，不代表实测用户准确率。本轮未测量性能改善，不作提速声明。

改动保留在工作区，未提交；未主动重写用户索引缓存，更新后的软件运行时会加载／重建 v11 索引。
