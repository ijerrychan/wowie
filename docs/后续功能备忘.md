# 性能基线与后续功能备忘

记录 2026-11-05 的启动器搜索基线优化和后续产品功能顺序。此文档用于分阶段规划，不代表后续功能已经实现。

## 本次基线优化

- UI 首屏仍为所有候选打分，确保匹配、收藏、分类和 provider 顺序保持一致；排名后使用部分选择，仅保留 UI 上限 256 条，再排序和复制结果。无界的 `search_in_context` API 保留原有行为。
- 匹配过程复用小写转换缓冲；ASCII 字段在关闭模糊搜索且精确、前缀和包含匹配均未命中时直接返回，跳过不必要的大小写转换。
- 这次没有改变文件搜索后端，也不引入自建索引。现有 Everything IPC 与 Windows Search 后备保持不变。

## 性能与内存验证待办

- `性能基准.md` 中的 10,000 项搜索数据是 2026-09-29 的 Windows debug 基准：连续查询 P50/P95 为 202.7/295.0 ms。该历史基准通过无界搜索 API，不衡量本次 UI 有界排名路径；本次未运行基准，因此没有声称新的耗时数字或改善比例。
- 下一次性能评估应增加 UI 首屏有界搜索的同机前后对照，并保留无界 API 基准；同时记录候选数、匹配数和 P50/P95。发布版数据需单独测量，不能与 debug 基准混用。
- 现有图标缓存、插件结果、后台任务队列、历史记录和 UI 行数都有各自上限，但目前没有全进程工作集、私有字节或堆峰值基线。后续在冷启动、索引完成、连续搜索和图标加载后记录这些指标，再决定是否需要进一步压低缓存或改索引表示。
- 仍需对所有候选执行匹配，当前搜索耗时仍随候选数量增长。只有基准确认匹配阶段占主要成本后，再评估来源侧候选检索或增量索引；不要仅凭合成数字增加常驻倒排/ngram 数据。

## 后续功能顺序

1. **浏览器书签搜索**：先支持常见浏览器的只读书签发现、搜索与打开；明确多配置文件选择，并避免写入浏览器数据库。是否扩展到浏览历史另行决定。
2. **窗口切换**：按窗口标题和所属进程搜索当前可见窗口，并提供切换到窗口的操作。关闭窗口可作为显式次级操作；结束进程不作为默认动作。
3. **系统工具组**：补充锁屏、睡眠、重启等可确认的系统操作，以及单位转换、日期时间、GUID、哈希和 Base64 等轻量工具。能通过现有 provider/plugin 接口实现的功能优先用该接口接入。
4. **文件工作流补强**：在现有 Everything / Windows Search 结果上增加类型、日期或大小筛选、预览和 Explorer / 文件对话框快速切换。此项不包括新建本地文件索引。
5. **插件发现与更新**：评估插件目录、安装和更新流程，并清晰展示插件权限与来源；等前述高频搜索功能稳定后再排期。

## 分阶段实施计划

每阶段由 Luna 子代理编写代码，主代理负责边界设计、差异审查和验证；完成一个阶段再进入下一个阶段，提交信息沿用仓库的 `type(scope): 中文说明` 格式。

| 阶段 | 可交付范围 | 验收重点 |
| --- | --- | --- |
| 1：浏览器书签 | Windows Chrome / Edge 的多配置文件书签发现、名称/文件夹搜索和默认浏览器打开 | 只读、有界解析；搜索按键不触发同步磁盘扫描；支持损坏文件与无浏览器环境；稳定身份与重复记录处理 |
| 2：窗口切换 | 当前用户可见窗口的标题/进程搜索与前台切换 | 排除启动器自身及无效窗口；窗口关闭后的失效处理；不把结束进程作为默认动作 |
| 3：系统工具 | 先补锁屏和轻量日期/单位转换，再扩展需要确认的睡眠、重启等操作 | 通过现有 Action/Provider 接入；危险操作明确确认；工具结果便于复制；不阻塞 root search |
| 4：文件工作流 | 基于现有后端完善筛选、预览和目录切换 | 保持 Everything / Windows Search 后端；媒体读取有预算与取消 |
| 5：插件管理 | 目录发现、安装更新与来源/权限展示 | 独立评估分发协议和更新回滚后再实施 |

第一阶段先支持 Chromium JSON 书签文件；Firefox 与浏览历史后续单独评估，以避免首阶段引入数据库依赖和更大的读取范围。每阶段只运行相关行为测试；共享协议或执行层变化时再扩大验证范围。性能改善比例与进程内存数字必须来自实际测量。

### 第一阶段实施记录

Chrome / Edge 书签 Provider 已由 Luna 实现并经主代理审查，自动加入非空 root 搜索。启动时后台预热，后续查询最多每 5 分钟触发一次后台刷新；读取失败保留该配置最后一次成功数据。当前支持标准安装目录中的 Default / Profile 配置，最多 32 个配置和合计 5,000 条书签；文件读取上限 16 MiB，只接受 HTTP(S) URL。URL 路径大小写和 fragment 均保留。

2026-11-05：书签模块 4 项测试通过，覆盖嵌套文件夹、URL 打开、损坏与缺失数据、URL 身份及失败后恢复；格式检查通过。尚未完成真实浏览器桌面验证，首次后台预热完成后需再次查询才能显示新快照，刷新完成不会主动改写当前结果列表。浏览器配置选择界面、Firefox 和浏览历史仍待后续阶段实现。

### 第二阶段实施记录

Windows 窗口搜索与切换已由 Luna 实现并经主代理审查。非空 root 查询可以按窗口标题或进程文件名搜索，选中后切换到对应窗口；最小化窗口先请求恢复。枚举最多返回 512 个可用窗口，排除当前进程、桌面、Shell、不可见窗口、工具窗口、cloaked 窗口与无标题窗口。执行前重新检查窗口句柄、PID 和可见状态；Windows 拒绝激活时显示本地化错误。

窗口使用类型化动作而非 Shell 路径，不提供收藏、管理员启动或打开所在目录操作。本阶段不提供关闭窗口或结束进程。其他平台返回空窗口列表。

2026-11-05：全量测试 221 passed、0 failed、9 ignored（总计 230 项），覆盖新增过滤规则、动作目标、序列化和上下文菜单语义；格式检查通过。测试未主动切换用户桌面窗口，实际焦点切换、最小化恢复和提升权限窗口的兼容性仍需桌面回归。下一阶段为系统工具组。

### 2026-11-06：书签发现与结果类型修正

用户反馈书签不可见，窗口与普通结果难以区分。本机只读诊断确认 Firefox 存在 280 条 HTTP(S) 书签，旧实现只支持 Chrome / Edge，未覆盖实际使用的浏览器；首次后台加载也没有触发当前查询刷新。

参考来源与取舍：

- [PowerToys Run Window Walker](https://learn.microsoft.com/en-us/windows/powertoys/run#window-walker-plugin) 使用 `<` 专门搜索窗口；[官方结果转换实现](https://github.com/microsoft/PowerToys/blob/main/src/modules/launcher/Plugins/Microsoft.Plugin.WindowWalker/Components/ResultHelper.cs)用窗口标题和运行进程副标题区别结果。Wowie 保留 root 聚合搜索，同时提供窗口专用会话，并以语义类型标签区分已打开窗口与应用启动入口。
- Flow 的[书签插件入口](https://github.com/Flow-Launcher/Flow.Launcher/blob/dev/Plugins/Flow.Launcher.Plugin.BrowserBookmark/plugin.json)提供专用触发词，[结果展示](https://github.com/Flow-Launcher/Flow.Launcher/blob/dev/Plugins/Flow.Launcher.Plugin.BrowserBookmark/Main.cs)使用书签名称、网址和网站/书签图标。Wowie 提供可见书签入口、专用会话和来源信息，避免只能在混合结果中碰巧找到书签。
- [Flow Firefox 加载实现](https://github.com/Flow-Launcher/Flow.Launcher/blob/dev/Plugins/Flow.Launcher.Plugin.BrowserBookmark/FirefoxBookmarkLoader.cs)使用数据库副本避免浏览器锁冲突。Wowie 的 Firefox 解析同样封装在书签 Provider 内，原目录只读，并包含 WAL 副本以读取活动浏览器数据。

本轮设计要求：分类扩展使用通用 `ResultCategory`，图标仍由 `IconSpec` 和共享后台图标服务解析，入口使用现有 `EnterSearchEngine` / session 接口。后台数据完成后通过通用 provider 内容代次通知重新呈现当前查询，不在 UI 内识别某个 Provider ID。窗口图标优先使用所属进程的可执行文件图标，访问失败时回退到窗口图标；书签有独立类型标识，网站 favicon 缓存不在本轮范围。

入口提示与分类必须分离：`bm`、`<` 是进入引擎的触发词，只通过现有 `shortcut_hint` / `shortcut_prefix` 显示在入口行。入口不是实际书签或窗口，归为普通入口类别；实际 URL 书签与窗口切换结果才使用 `Bookmark` / `Window` 分类及文字类型标识。会话内结果不重复入口触发词，类型标识也不采用按键卡片样式。

实现和验证：已补充 Firefox、Brave、Vivaldi 与 Chromium 标准目录发现，Firefox 仅查询书签及其网址/父文件夹。数据库和 WAL 通过流式有界复制到专属临时目录；读取完成关闭连接并清理副本。SQLite 单独设置忙等待、单值大小和查询时间上限，刷新失败保留上次成功数据。此来源增加 `rusqlite`（bundled、limits、hooks），依赖只用于 Provider 数据读取，Core 和 UI 不解析浏览器数据库。

完成后，通用 provider 内容代次会通知现有刷新循环更新当前查询，首次加载不再要求再次输入。输入触发词的隐式会话使用已解析的 argument；显式进入会话后保留原输入。入口和实体结果的分类、触发提示均有独立测试。

2026-11-06 验证：全量测试 233 passed、0 failed、10 ignored；另行运行 Firefox 实机只读诊断，加载 280 条 HTTP(S) 书签，仅输出数量。Clippy（all-targets，`-D warnings`）、格式与差异检查通过。布局 smoke 覆盖 520px 宽、20 号字、中英文类型文字并检查布局诊断；尚不代表所有实际 DPI 下的视觉效果或窗口焦点行为已完成桌面回归。
